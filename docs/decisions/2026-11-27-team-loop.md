# One task goes through a pull request, then a binary is uploaded only when an app changed

## Decision

"Let's go" runs the lowest Ready task through a branch, a failing test commit, the implementation, and a pull request. The author asks the user for a missing fact or credential, including a Firebase JSON, and waits. The author does not invent it. The user starts a new chat and says "let's go" to review and merge after checks are green. After that merge, an `androidApp` or `iosApp` change is uploaded to Firebase App Distribution and TestFlight when `docs/distribution/REQUIRED.md` has values. The session does not start the next task. The app does not gain the Firebase SDK.

## Why

Five sessions committing to `master` overwrite each other, and a review in the author's chat cannot see GitHub checks. The user starts work with one sentence, so the loop has to be in the repo. Uploading every shared-library commit would ship a binary that did not change. Uploading with an invented Firebase app id or Apple team would put a build on the wrong account.

## Other ways

- Commit on `master` and review the local diff. One session is simpler, and parallel tasks collide with no check to wait on.
- Upload a binary only for a final store release. Internal testers would not see each app change, and TestFlight would be a separate project at the end.
- Add the Firebase SDK so the app checks in with App Distribution. That puts Firebase inside MealIn. Distribution here is the `firebase` CLI on a file Gradle already built. Remote Config stays out.

## Stood on

- `docs/tasks/README.md` already gives one task to one session and a different session for review.
- `docs/decisions/2026-11-27-no-store-and-health-services.md` keeps Remote Config, billing, and the Firebase product surface out of the app.
- Task 005 is the GitHub Actions workflow. It is not on a remote yet. This decision does not pretend those checks already run.
- `docs/distribution/REQUIRED.md` lists the credential names and no values.
